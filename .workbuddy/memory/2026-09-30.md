## Windows 内置 OCR 实测（关键结论）
- **系统 OCR 引擎可用**（`Windows.Media.Ocr`）：`AvailableRecognizerLanguages` 仅 `zh-Hans-CN`（Count=1）；`MaxImageDimension=10000`。
- **`en-US` 不可用**：`TryCreateFromLanguage('en-US')` 返回 null，`IsLanguageSupported('en-US')=False`；`C:\Windows\OCR` 仅有 `zh-cn` 目录。
- **结论**：Windows OCR 是**单语言引擎**，本机只能识别中文界面；英文安装器（Inno/NSIS 英文版）的 OCR 定位不可靠 → 英文界面优先 UIA + 图像模板，镜像需补 `en-US` 语言包。
- 产出一键验证脚本 `scripts/verify-ocr.ps1`（列语言 / 查目录 / 生成中英测试图 / 端到端识别并输出像素包围盒），已作为交付物 D10 记入 PRD，结论回填为 C19 并改写 F16.3（P0）。

### 语言选型论证留档（回答"为什么用 Go 而不是 Python"）

- 结论：**决定性因素是交付形态，不是性能**。新增 PRD 7.1.1 节 + 决策 C26。
- ① 交付形态硬约束（一票决定）：需求是"单 exe 拷贝即用 + 无残留"；Python 无真静态编译路径，PyInstaller 单文件模式 = bootloader + 压缩归档，**运行时解压到 `%TEMP%\_MEIxxxx`**，与 DC1 / 第 6 节"无残留"验收直接冲突；体积 30~100MB+、首次启动 1~3 秒亦不合格。Go `CGO_ENABLED=0` 真静态链接、无释放无残留。
- ② 反病毒友好性（本项目特有，权重高）：工具行为特征（批量执行任意文件、模拟键鼠、写注册表）已被 11 节列为高风险项，**PyInstaller/Nuitka 的 bootloader 是被恶意样本滥用过的载体，AV 误报重灾区**，叠加等于二次加险。Go 静态二进制无打包器特征。
- ③ Win7 下 Python 处境更差：官方文档明确 **3.9+ 要求 Win8.1+，"If you require Windows 7 support, please install Python 3.8"**，而 **Python 3.8 已于 2024-10 EOL**；Go 是 1.20.x（2023-02 发布）。社区 PythonWin7 类重编译包属非官方产物，供应链风险不可接受。
- ④ GIL 使 CPU 密集的图像处理/模板匹配无法真并行；改 multiprocessing 又与 PyInstaller 单文件冲突。
- ⑤ 强类型 + 内建工具链（gofmt/vet/golangci-lint/cover）贴合"代码规范、高内聚低耦合"要求；适配层大量 `syscall`/COM 操作，编译期检查价值最高。
- 客观评估 Python 强项并说明为何被消解：**OCR 与 GUI 生态优势在本方案已被"OCR 走外部独立进程（PaddleOCR-json）"+"GUI 直接调原生 Win32/UIA API"两项决策架空**；pywinauto 的 Win7 覆盖度同样取决于系统 UIA 能力而非语言库。
- 关键附加结论：**即使 Q10 确认目标环境不覆盖 Win7，与 Win7 无关的 ①② 两条理由依然成立，语言应维持 Go**（版本可升至 1.21+）。

### 新增 F17 软件包结构识别与安装入口优先级排序（回答"是不是就不用一个一个尝试了"）

- 用户洞察：输入是压缩包/目录时，应先识别目录结构，包内可能已有 install.bat 等明确入口，不必逐个盲扫。**判断：应该做，但最大收益不是效率而是正确性。**

### OCR 自检脚本重写（verify-ocr.ps1）+ PRD v2.10

- 用户问 `scripts/verify-ocr.ps1` "是不是不需要了"。**结论：不是不需要，而是内容过时**——原脚本（v2.3）只验证 `Windows.Media.Ocr`，而内置 OCR 已在 v2.4 降为**默认关闭的可选回退后端**（DC8）。PRD 两处（F16.3 参考工具、交付物 D10）本就标注"M1 需扩展为多引擎探测 + 端到端验证"，故本轮**重写而非删除**。
- **重写要点**（`scripts/verify-ocr.ps1`，约 800 行）：
  - 覆盖 `paddleocr_json`（默认）/ `rapidocr_json` / `umi_ocr`（走 HTTP `127.0.0.1:1224/api/ocr`）/ `tesseract`；`windows` 内置 OCR 保留为 `-Engine windows` 可选回退。
  - 引擎发现优先级：`-EnginePath` → `config.json` 的 `ocr.engine_path`（同目录/上级/当前目录自动找）→ PATH → 常见路径（`-Depth 2` 浅扫）。
  - **实际启动一次**做能力自检（版本 / 耗时 / 语言 / 可用调用方式），生成中英混排测试图（下一步/上一步/取消/安装/浏览/我接受/Next/Install/I Agree + 一个按钮外框）做**端到端识别**，输出文本 + **中心像素坐标** + score（PaddleOCR 系为四角坐标取中心）。
  - PaddleOCR 系额外探测 **stdio 管道模式**（无参启动 + 写一行 `{"image_path":...}` + 关 stdin 触发 EOF 退出）；CPU **AVX/AVX2** 探测（kern32 `IsProcessorFeaturePresent` 39/40），无 AVX 时提示切 `rapidocr_json` 并跳过 Paddle 实际启动。
  - `-Json` 时结构化结果走 **stdout**、人类可读报告走 **stderr**（对齐 F10.1 三通道），退出码 **0 / 5** 与 `--check-prereq` 语义对齐。
- **踩坑（重要）**：**含中文的 .ps1 必须以 UTF-8 with BOM 保存**。PS 5.1 对**无 BOM** 的 UTF-8 脚本按 ANSI(GBK) 解码 → 中文串尾字节吃掉引号 → 实测报 **54 处虚假语法错误**（全是 `UnexpectedToken`/`MissingEndCurlyBrace` 之类），加 BOM 后 **0 错误**。修复方式：`[IO.File]::WriteAllText($f, $txt, (New-Object System.Text.UTF8Encoding($true)))`。**注意：本项目 .md 文档保持 LF + 无 BOM，勿混用。**
- **本机实测**（sandbox，PowerShell 5.1 / Win10 build 26200 / i7-13700H）：AVX 与 AVX2 均支持；未安装任何 OCR 引擎 → 4 个引擎全部 `MISS`，正确给出离线安装指引与 `退出码 5`；`-Engine none` → `ok:true`、退出码 0；`-Json` 输出可被 `ConvertFrom-Json` 正常解析。
